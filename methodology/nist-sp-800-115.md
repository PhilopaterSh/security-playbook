# NIST SP 800-115: Technical Guide to Information Security Testing and Assessment

> [!warning] Age and authority
> This guide was published in September 2008. Use it as foundational process guidance for assessment planning, execution, analysis, evidence handling, reporting, and remediation. It is a broad information-security assessment guide, not a current web-application test catalog, a source of current tool syntax, or authorization to test a target.

## Original Document

- Official NIST PDF copy stored in this Vault: Attachments/Documents/Cybersecurity/NIST SP 800-115.pdf. The [NIST publication record](https://csrc.nist.gov/pubs/sp/800/115/final) remains the authoritative online source.

## Purpose and Scope

NIST SP 800-115 describes technical information-security assessment techniques and recommends ways to plan assessments, execute them, analyze results, and develop mitigation strategies. Its scope includes systems and networks, with application-security testing treated as one component; it is not limited to web applications. (NIST SP 800-115, §1.2, printed p. 1-1; §2.1, pp. 2-1-2-2.)

The useful contribution to this vault is the assessment-process layer: it helps connect authorization and planning to controlled testing, evidence analysis, reporting, and follow-up. Use the versioned test cases in the Web Application Penetration Testing Checklist and the [OWASP WSTG v4.2](https://wstg.owasp.org/v4.2/) for web-specific procedures; NIST SP 800-115 does not replace their coverage or version identifiers.

## Assessment Technique Classes

NIST groups technical work into three complementary classes. No single technique provides a complete picture, so the assessor selects and combines methods according to the approved objective, constraints, and risk. (NIST SP 800-115, §2.2, pp. 2-2-2-3.)

| Class | What it answers | Examples in the guide | How to use the result |
|---|---|---|---|
| **Review techniques** | What can be learned by examining existing evidence or configuration? | Documentation, logs, rulesets, system configuration, network traffic, and file integrity (§3, pp. 3-1-3-5). | Record observations and gaps; a review may identify a concern without proving an exploitable vulnerability. |
| **Target identification and analysis** | Which systems, services, or potential weaknesses merit examination? | Network discovery, service identification, vulnerability scanning, wireless analysis, and application-security examination (§4, pp. 4-1-4-10). | Treat scanner and discovery results as candidates that need context and, where appropriate, validation. |
| **Target vulnerability validation** | Does the suspected weakness exist, and what security exposure does it produce? | Penetration testing and other validation methods (§5, pp. 5-1-5-7; application security is also discussed in Appendix C, beginning at C-1). | Validate only within the approved scope and stop after obtaining the minimum evidence needed to support the claim. NIST identifies this class as higher risk than review or identification work (§7.1, pp. 7-1-7-2). |

This distinction supports the field guide's result states: a tool alert or unusual response is a lead; a finding requires evidence that supports the claimed behavior and impact. See Web Application Penetration Testing Field Guide#Decision Guide for Unclear Results.

## Assessment Lifecycle

NIST presents assessment work as planning, execution, and post-execution (§2.1, pp. 2-1-2-2). Its example penetration-testing model breaks the work into planning, discovery, attack, and reporting, with additional discovery feeding back into later testing (§5.2.1, pp. 5-2-5-4). These are adaptable models, not mandatory phases for every engagement.

| Stage | Work to complete | NIST source |
|---|---|---|
| **Plan** | Set objectives, scope, constraints, roles, schedule, logistics, selected techniques, risk controls, and deliverables. Document rules and approvals before testing. | §§5.2.1, 6.1-6.6, pp. 5-2, 6-1-6-12; Appendix B, beginning at B-1. |
| **Identify and analyze** | Gather information, identify targets and candidate weaknesses, and compare observations with the assessment objective. Keep the method proportionate to the system and risk. | §§4, 7.2-7.3, pp. 4-1-4-10, 7-2-7-4. |
| **Validate** | Use an approved validation technique to confirm a candidate and establish the actual exposure. Coordinate with the system owner and respect stop conditions. | §5, pp. 5-1-5-7; §7.1, pp. 7-1-7-2. |
| **Report and follow up** | Analyze root causes, document findings and limitations, recommend mitigations, and track remediation or retest actions as agreed. | §§8.1-8.3, pp. 8-1-8-3. |

## Planning and Rules of Engagement

NIST emphasizes that the assessment plan or Rules of Engagement (ROE) should govern test activity. Its planning chapter covers assessment objectives, technique selection, logistics, plan development, and legal considerations (§§6.1-6.6, pp. 6-1-6-12). Appendix B provides an illustrative ROE template; it begins with purpose, scope, assumptions and limitations, and risks, then addresses personnel and logistics (Appendix B, pp. B-1 onward).

For a live engagement, make sure the written authorization and ROE identify, at minimum:

- Exact in-scope systems, hostnames, applications, accounts, and excluded assets.
- Permitted test methods, prohibited activity, request limits, time windows, and stop conditions.
- Named points of contact, escalation route, incident coordination, and reporting channel.
- Evidence collection, access, storage, transmission, retention, and destruction requirements.

These are planning prompts, not permission inferred from the publication. The target owner's current written authorization and engagement-specific rules remain controlling. For this vault's actual workflow, use Web Application Engagement Record Template and Web Application Penetration Testing Field Guide#Starting the Assessment: Preconditions.

## Execution, Analysis, and Evidence Handling

During execution, NIST recommends following the assessment plan or ROE, coordinating with relevant owners, analyzing results throughout the work, and handling collected data securely (§7.1-7.4, pp. 7-1-7-7). The guide calls out collection, storage, transmission, and destruction as separate data-handling concerns (§7.4.1-7.4.4, pp. 7-5-7-7).

Applied here, keep only the minimum evidence needed to reproduce a finding, sanitize credentials and personal data before recording it, restrict access to raw captures, and follow the engagement's retention and cleanup requirements. If a test causes an incident or unexpected service impact, stop and use the agreed escalation process; do not continue simply because a checklist includes the test.

## Reporting, Mitigation, and Retest

NIST recommends final analysis, root-cause consideration, mitigation recommendations, and a report that can support corrective action and follow-up (§§8.1-8.3, pp. 8-1-8-3). A useful report separates the observed behavior and supporting evidence from interpretation, impact, limitations, and proposed remediation. Match the level of detail to the technical and management audiences, and track actions through the agreed owner and retest process.

For vulnerability submissions and the vault's report format, follow Vulnerability Reporting and Differential Verification Standard. NIST's reporting chapter is general process guidance; it does not define current platform-specific submission fields or severity scoring.

## Limitations

- The publication dates to 2008. Tool examples, product versions, protocols, and technical recommendations may be obsolete; verify current behavior with authoritative documentation before using any technical detail.
- It is a general information-security assessment guide. Use the specific WSTG case and the actual application's technology for web testing.
- A technique's appearance in this guide does not make it safe, applicable, or authorized for a particular assessment.
- NIST describes frameworks and examples; this vault's workflow is an adaptation aligned to the current engagement record, checklist, and program or client rules.
